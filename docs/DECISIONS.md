# Decisions and open items

## Decisions

- **The proof shows the selected AI image**, as requested. Everything else on the proof is exact:
  - Lifted from the real Liquid Mercury proof as untouched vector art: the mounting diagram, footer rule, impactsigns.com wordmark and disclaimer.
  - Drawn by code at the measured positions: the dimension brackets and labels.
  - Pulled from `assets/`: the finish and paint-fill icons.
- **One layout engine drives everything.** The concept image is generated from an exact layout drawing (Reference 1), and the vector production PDF is built from the same layout. The vector file therefore matches the concept you pick without tracing an AI image, which would produce unusable artwork.
- **Classic layout = the real Heritage job.** Measured from `production_32241.ai`:
  - image frame 0.542 × plaque width, at the photo's own aspect ratio
  - body 46.3 pt with a 64.6 pt line pitch
  - headline 56.3 pt, subhead 50.1 pt
  - ¼″ border
  - the whole stack centered in the field

  The automated test holds it within 2 pt of the real file.
- **Three layouts:**
  - **Classic:** the standard proportions.
  - **Feature Image:** a larger image.
  - **Statement:** a larger headline and a more compact image.

  Landscape photos on landscape plaques sit on the left with text on the right. Logos default to the bottom when there is a portrait image, otherwise the top. Designers can override this.
- **Spec parser is rule-based (no AI).** It only ever picks options that exist in `data/catalog.json` and labels every guess "Assumed":
  - "relief image" → Photo Relief
  - border not specified → Single Line
  - font not stated → Times New Roman
  - "Dark Oxide or Leatherette" → Dark Oxide paint with Leatherette texture
- **Wording is never changed.** Only leading and trailing spaces are removed, and each removal is reported. Straight quotes stay straight (the real Heritage plaque uses `'Onward'`).
- **Spell check before proof.** The image model draws its own letters, so each concept is read back by a vision model and compared word by word. A proof cannot be made from an image with differences unless the designer explicitly confirms.
- **Image-type examples follow the uploaded file names.** Photo Relief = the bronze man with glasses, Etched = the dark sepia man in a suit, Full UV = the color photo, Bas Relief = the sculpted soldier. Checksums match the files pasted in chat.
- **Logos in the production file are traced to vector.** Anything that is not near-white becomes raised metal, so colored logo parts are kept. A logo supplied as SVG/PDF/AI is rendered at high resolution first, then traced. Preflight always asks for a visual check.
- **Proof footer keeps the vector "impactsigns.com" wordmark** from the real proof. The uploaded logo (without ".com") is used in the app header. Add `brand-assets/proof-footer-logo.svg` to override the footer.
- **Fonts:** licensed files go in `brand-assets/fonts/`. Until then these open stand-ins are used and flagged:
  - Tinos for Times (identical letter widths)
  - EB Garamond for Garamond
  - Crimson Pro for Minion
  - Libre Franklin for Franklin
  - Arimo for Helvetica
  - Source Sans 3 for Myriad
- **Aluminum:** see Round 2 below; the current catalog includes Cast Aluminum and Brushed Aluminum.

## October 5, 2026: several photos, logos and sketches per job

- **Lists, not single files.** A job holds `photos[]`, `logos[]` and `sketches[]` (`shared/uploads.ts`, `shared/types.ts`), each file with its own id, original name and a SHA-256 of the original. Limits: 4 photos, 6 logos, 4 sketches per job (`UPLOAD_LIMITS`). Jobs and version snapshots saved with one `photo` / `logo` / `sketch` are upgraded to one-item lists when read (`upgrade`, `upgradeConcept` in `server/db.ts`), so old jobs, "Use this version" and Undo keep working. Snapshots are compared in a fixed key order.
- **Every photo and logo is on the plaque.** Photos are one group of frames, logos one row; each keeps its upload order (left to right, then top to bottom). Designers reorder with ‹ / › and remove one file at a time. The placement controls (image after a wording line, logo slot) and the Fix adjustments (`imageScale`, `logoScale`) apply to the whole group. Per-file positions (one logo at the top, another at the bottom) are not supported; a Fix request about one of several files is an image-only edit, and add / remove / swap requests are refused with a pointer to Customer files (the image model must never add or drop a customer file the vector file does not have).
- **Layout of a group** (`arrangePictures` in `server/layout/engine.ts`): all pictures of a group share one height and keep their own proportions; the arrangement (one row, or two rows) that makes them largest wins, but extra rows must gain at least 25% in area, so a pair of portraits stays side by side. Photos may use two rows; logos two rows only from four. Gaps between pictures are 0.035 (photos) / 0.03 (logos) of the shorter plaque side, at least 0.15 in. Two landscape photos on a landscape plaque stack in the left column; more photos go in a group above (or between) the text. Several photos get a wider width budget (up to 1.8 x the single frame, never more than 92% of the field) and, unlike the single frame, their height also shrinks as the type shrinks so text keeps room.
- **One photo and one logo are unchanged.** With a single picture the arranger uses the original arithmetic (frame width first, capped by the height limit). All golden tests (Heritage within 2 pt) pass unmodified apart from the input shape, and every sample proof and plaque rendered pixel-identical to the committed samples (only the caption bar's system font differed in this environment, so the samples were not re-committed).
- **Image model references stay within 16.** Each photo and logo is its own reference, named by its place in Reference 1 ("left", "top-right", …, from `placeNames`). If the files would exceed the limit, the sketches and then the logos are combined into one numbered sheet each (`contactSheet`); with the maximum files (4 photos, 6 logos, 4 sketches, face-screw mounting) a request has 13 references. The concept prompt says how many frames and logos there are and that each shows only its own file.
- **Logos in the layout drawing are shown as cast.** Near-white parts of a logo (luminance 215 and above, the same threshold the vector tracer uses) are drawn as recessed field, not as white boxes. This also applies to single-logo jobs and makes Reference 1 agree with the production file.
- **Production file:** one placeholder window per frame; each logo is traced separately and centered in its own box, with a note per logo naming the file. Preflight reports "All 3 traced to vector" or how many positions have no file. The Description-sheet header says "Includes 2 photo relief images." when there are two frames.
- **Uploads are safe to send together.** The browser sends the chosen files one after another (one request each, so a big file is held in memory once and every file gets its own answer). The server reads each file without holding the job, then adds it to a freshly loaded copy, so files sent at the same time (or a change made meanwhile in another panel) are all kept. A file that cannot be read is refused before anything is written to the job. Removed files stay on disk for the versions that used them.
- **Unverified:** these layouts were checked in demo mode (layout drawings, proof and vector PDF) and by tests, not yet with paid live images. Live behaviour of the image model with two or more portraits (keeping each likeness in its own frame) still needs a paid check with `scripts/verify-live.mjs`.

## October 5, 2026: donor-list plaques and the vector production file

- **Problem:** on text-heavy plaques (donor walls) the vector file did not look like the concept. A pasted list becomes one body paragraph per name; the layout stacked them in a single column with paragraph gaps, then held every line at the ¼" minimum and kept going, so the names ran off the top and bottom of the plate. Nothing flagged it, and the image model (which is shown the layout drawing) had no sensible arrangement to follow.
- **Auto columns, in the layout engine** (`fitLayout` / `computeCore` in `server/layout/engine.ts`): runs of eight or more short single-line body paragraphs (or one body block of eight or more short lines) are a donor list. The engine fits the list in one column and in two to five, and uses columns only when the whole plaque fits at a legal size *and* the type is at least 15% larger than one column allows; otherwise the pasted one-column layout is kept. Because the layout feeds Reference 1, the proof and the vector file, all three get the same arrangement. The words are not edited: only how the lines are placed changes (column order is top to bottom, left to right). A block the designer already set in columns is left alone.
- **Tier headings:** in a mixed-case list, a line in capitals (PLATINUM, GOLD) is a heading, not a name: it breaks the list and each group gets its own columns. A list written entirely in capitals stays one list.
- **Column fit:** the ¼" floor used to lift column type back above what its column holds, so neighbouring names touched. That now counts as "does not fit" and another column count is tried.
- **Honest failure:** `server/layout/check.ts` measures each line's real ink box (glyph ascenders, accents and tails) and reports lines past the border, lines on top of each other, and lines on a photo or logo. These become layout warnings, and preflight has a new hard check, "Everything fits on the plaque" (not warn-only). A 12" x 18" plaque with 80 long names cannot be cast at ¼" letters; it now says so instead of producing a file that is silently cut off.
- **Reference jobs unchanged:** all 11 reference production files render pixel-identical to before; no measured proof or production constant was touched. `capHeightRatio` moved to `server/text/fonts.ts` (re-exported from the engine) so the check can use it.
